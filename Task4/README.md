## Часть 1. Rate limiter

### Что было не так
- **Одна зона `one` на 100 r/s для всех.** Веб и мобильное приложение делили один лимит, причём вдвое-втрое выше нужного.
- **`burst=200` при 100 r/s.** Позволял клиенту послать 200 запросов сверх лимита разом.
- **Ответ 503 по умолчанию.** Клиент не отличит «вы превысили лимит» от «сервер упал».

### Как исправлено
1. **Канал определяется по заголовку `X-Client-Type`** (`web` / `mobile`), его выставляют приложения. Неизвестный или пустой канал считается мобильным, то есть получает более строгий лимит. Так без заголовка ограничение не обойти, а неизвестный клиент (например, будущий партнёрский API, пока для него не заведён свой лимит) не получит больше мобильного.
2. **Две зоны с ключом по IP:**
   - `web_per_ip` — 50 r/s;
   - `mobile_per_ip` — 30 r/s.

   Через `map` запрос получает непустой ключ только в зоне своего канала. Запросы с пустым ключом nginx не учитывает, поэтому каждый запрос считается ровно в одной зоне.
3. **`burst` = половина секундного лимита (25 и 15) с `nodelay`.** Экран приложения при открытии шлёт пачку параллельных запросов, burst пропускает её без задержки. Средняя скорость при этом не превышает лимит.
4. **`limit_req_status 429`** — стандартный код «Too Many Requests», клиент может сделать паузу и повторить.
5. **В бэкенд передаётся определённый канал (`X-Client-Channel`)** — для метрик и логов.

Новые каналы (сайт, чат-бот, партнёрский API) добавляются строкой в `map` и своей зоной.

### Проверка
k6 подаёт постоянную нагрузку 100 r/s с одного IP в течение 10 с:

| Канал | Пропущено (200) | Отклонено (429) | Ожидание |
| :- | :-: | :-: | :- |
| `X-Client-Type: web` | 526 | 475 | 50 r/s × 10 с + burst 25 + 1 = 526 |
| `X-Client-Type: mobile` | 315 | 685 | 30 r/s × 10 с + burst 15 = 315 |
| без заголовка | 315 | 685 | как mobile |

### Ограничение
Заголовок канала выставляет клиент, его можно подделать. Подделка даёт максимум 50 r/s вместо 30, и это всё равно лимит на IP. Чтобы канал нельзя было подделать, веб и мобильное приложение можно развести по разным доменам или server-блокам (`api.novamarket.ru` / `m-api.novamarket.ru`) либо брать канал из claim'а JWT, проверенного на gateway.

## Часть 2. Circuit breaker

### Что было не так
- **Таймауты 30 с.** Каждый запрос пользователя к недоступной логистике висел полминуты.
- **Повторы к сломанному сервису.** Не было механизма перестать ходить в сломанный сервис: каждый запрос заново ждал таймаут.
- **Нет контролируемого ответа.** Клиент получал 502/504 вместо понятного ответа.

### Как исправлено
- **Таймауты** `proxy_connect_timeout`, `proxy_send_timeout` и `proxy_read_timeout` — 3 с.
- **Breaker на пассивных проверках здоровья NGINX:**
  - `server logistics.company.com max_fails=5 fail_timeout=30s`. Неудачей считаются ошибка соединения, таймаут и ответы 500/502/503/504 (`proxy_next_upstream`);
  - **открытие:** после 5 неудач в окне 30 с сервер исключается из балансировки на 30 с, и запросы к нему не идут;
  - **полуоткрытое состояние:** через 30 с nginx пропускает к логистике пробный запрос. Если запрос успешен, вызовы восстанавливаются. Если нет, сервер снова исключается на 30 с.
- **Fallback.** Пока breaker открыт, запрос сразу получает `503` с JSON `{"code":"LOGISTICS_UNAVAILABLE",...}` и заголовком `Retry-After: 30`. Delivery Service отличает этот ответ от ошибки и ставит заявку в очередь повторов (см. Saga в задании 1).
- **Почему fallback сделан резервным сервером (`backup`), а не только через `error_page`.** NGINX игнорирует `max_fails` и `fail_timeout`, если в `upstream` один сервер: такой сервер никогда не считается недоступным. Без второго сервера breaker не открывался бы, и каждый запрос по-прежнему ждал бы 3 с. Резервный сервер — локальный `server` на `127.0.0.1:8081`, который отвечает fallback'ом:
  - трафик на него идёт, только пока основной исключён или не ответил;
  - `max_fails=0` — сам fallback никогда не исключается.

  `error_page 502 504` страхует случаи, когда nginx не передаёт запрос на резервный сервер, например неидемпотентный POST.

### Проверка
Мок логистики работает в отдельной docker-сети под именем `logistics.company.com`, поэтому конфиг проверяется без изменений. Режим мока переключается по команде: `ok`, `slow` (ответ через 5 с), `error` (500).

| Сценарий | Результат |
| :- | :- |
| Логистика работает | 200 за 1–2 мс |
| Логистика отвечает через 5 с, запросы 1–5 | 503 fallback ровно через 3 с (таймаут) |
| 6-й и 7-й запросы | 503 fallback за < 1 мс — breaker открыт, в логистику не ходим |
| Логистика восстановилась, 30 с не прошло | 503 fallback — breaker ещё открыт |
| Через 31 с | 200 — пробный запрос успешен, вызовы восстановились |
| Логистика отвечает 500, 5 запросов подряд | 503 fallback, breaker открылся |
| Через 31 с логистика всё ещё отвечает 500 | пробный запрос неудачен — breaker снова открыт на 30 с |
| Логистика починилась, ещё через 31 с | 200 |

Лог мока подтверждает, что пока breaker открыт, запросы до логистики не доходят:
- в сценарии с таймаутами — ровно 5 запросов;
- в сценарии с ошибкой 500 — 5 запросов и 1 пробный.

### Ограничения open-source NGINX
- **«5 подряд» реализовано как «5 неудач в окне `fail_timeout` (30 с)».** При устойчивом сбое внешнего сервиса поведение то же, но редкие разрозненные ошибки, попавшие в одно окно, тоже могут открыть breaker. Строгий счётчик подряд идущих ошибок и метрики состояния breaker'а есть в NGINX Plus, Envoy или Istio (`outlierDetection.consecutive5xxErrors`).
- **Состояние breaker'а — в памяти каждого worker-процесса.** При нескольких worker'ах каждый открывает свой breaker после своих 5 неудач. Это немного увеличивает число запросов к сломанному сервису до открытия, но не ломает поведение. Если нужно общее состояние, в `upstream` добавляется `zone logistics 64k;`.
- **DNS-имя `logistics.company.com` резолвится при старте nginx.** Если у провайдера меняются IP, нужен `resolver` и параметр `resolve` у `server` (доступен в open-source nginx с версии 1.27.3).
